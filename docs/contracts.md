# Builder contracts

Exported functions, components and routes each slice provides for the others. Generated from the builders' reports; the code is the source of truth.

## Metrics (lib/metrics)

- import from "@/lib/metrics" (server only). Functions whose at is optional use one shared 'now' per request when it's omitted.
- isMemberActive(userId: string, clubId: string, at?: Date): Promise<boolean> — the attendance rule only (true for a regular guest as well); pair it with membership status when the question is about members.
- activeMemberIdsFor(clubId: string, at?: Date): Promise<string[]> — ids of ACTIVE members who are active per the rule.
- clubActivity(clubId: string, at?: Date): Promise<ClubActivity> — adds optional currentTermName / previousTermName. reasons lists each unmet requirement when the club is inactive, holds the pilot note while it's in its pilot period, and is empty when it's active on its own record.
- NEW clubActivityMany(clubIds?: string[], at?: Date): Promise<Map<string, ClubActivity>> — batch for admin tables; leave out ids for every approved club.
- clubRetention(clubId: string, period: 'month'|'quarter'|'academicYear'|'year', opts?: { count?: number; at?: Date }): Promise<RetentionPoint[]> — oldest first, ending with the period that contains at (inProgress: true). Default counts come from DEFAULT_RETENTION_COUNT = { month: 12, quarter: 8, academicYear: 4, year: 4 }; rate is null when the previous period had nobody.
- memberRetention(userId: string, clubId: string, period: RetentionPeriod): Promise<{ periods: number; attendedPeriods: number; rate: number | null }> — the period in progress counts only once they've attended in it.
- clubAttendanceByOccurrence(clubId: string, opts?: { from?: Date; to?: Date }): Promise<OccurrenceAttendance[]> — oldest first. Defaults to every occurrence that has started (pass a future to for upcoming ones). Includes events the club co-hosted. Adds an optional held: boolean.
- NEW clubMemberAttendanceCounts(clubId: string, opts?: { from?: Date; to?: Date }): Promise<Map<userId, MemberAttendanceCount>> — MemberAttendanceCount = { attended: number; lastAttendedAt: Date | null; active: boolean }. Covers every ACTIVE member (zeros if they haven't come) plus everyone who has attended. attended and lastAttendedAt respect the range; active is always as of now.
- memberClubSummary(userId: string, clubId: string): Promise<MemberClubSummary>
- NEW memberClubSummaries(userId: string): Promise<MemberClubSummaryEntry[]> — MemberClubSummaryEntry = { club: { id, name, slug, logoColor, logoUrl }; summary: MemberClubSummary; membershipStatus: MembershipStatus | null }. Lists ACTIVE memberships first, then clubs they only attended or have left; each group alphabetical.
- reviewEligibility(userId: string, clubId: string): Promise<{ eligible: boolean; attended: number; required: number }>
- clubListMetrics(clubIds?: string[]): Promise<Map<string, ClubListMetrics>> — one batched pass. With no ids it covers every APPROVED club; with ids it covers those clubs in any status. retentionRate compares the last complete campus month with the one before.
- networkData(opts?: { since?: Date; until?: Date }): Promise<NetworkData> — default window is the last 365 days (NETWORK_DEFAULT_DAYS), shared between visitors for 60 s. Nodes are APPROVED clubs sorted by name; majorName falls back to the club's focusOther. Edges are undirected, source < target, sorted by weight descending.
- platformSummary(at?: Date): Promise<PlatformSummary> — adds optional termName. activeClubs includes pilot clubs (activeClubs + inactiveClubs = approved clubs). eventsThisTerm = held events, university events included. monthlyCheckins = last 12 campus months, labelled like 'Oct 2026'.
- Re-exported pure helpers: isActiveStudent(standing: { lastAttendedAt: Date|null; latestRank: number|null }, at: Date, rule: { windowDays: number; recentEvents: number }): boolean; pilotPeriodEnd(createdAt: Date, terms: TermLike[]): Date | null; attendanceRate(memberAttendees: number, membersAtTime: number): number | null; retentionRate(retained: number, previous: number): number | null; checkinLines(participants: string[], memberOf: string[]): [string, string][]
- Client-safe types: import type { ClubActivity, RetentionPoint, OccurrenceAttendance, MemberClubSummary, MemberClubSummaryEntry, MemberAttendanceCount, ClubListMetrics, NetworkNode, NetworkEdge, NetworkData, PlatformSummary, RetentionPeriod } from "@/lib/metrics/types" (also re-exported from "@/lib/metrics"). The pure rules are in "@/lib/metrics/pure", which has no server imports.

**Decisions:**

- Active student is 'attended in the window OR attended one of the club's last N events'. I read 'whichever is later' as: someone stays active until whichever comes later, N days after their last check-in or the moment that event drops out of the club's last N events. That is the same as the OR the contract describes; the stricter AND reading would have marked nobody active in clubs that meet every other month. The window is inclusive, and 'last attended' means the event's start time, not when the check-in was recorded.
- Event times are occurrence start times throughout, so a leader's late manual add counts on the day of the event.
- A held event is a SCHEDULED occurrence that has started and has at least one check-in, from an event that isn't a draft. Past occurrences of an event cancelled later still count when people checked in. Activity score counts only occurrences of events still SCHEDULED (host or approved co-host), from 30 days back to 30 days ahead.
- The active-club event minimum must be met within one term on its own (current term or previous activity term); it is not summed across the two. Current term = the term containing now, or the latest term between terms. Previous = the activity-counting term before it (summer skipped when it doesn't count).
- The pilot period ends at the end of the first activity-counting term that starts after creation, measured from creation as the contract says, and applies only to APPROVED clubs. If the calendar has no such term yet, the club counts as in its pilot with pilotEndsAt = null.
- A term end stored at campus midnight is treated as covering that whole day, so events on the last day count.
- Members at the time of an event: joinedAt at or before the start, not ended by then, any status except PENDING or DECLINED. Someone auto-enrolled by their first check-in joined after the start, so they count as a guest at that first event. This keeps member check-ins as a subset of members at the time, so the rate never exceeds 100%.
- 'Since joining' starts at the earlier of joinedAt and the first check-in, so guests who later join keep their history. A membership that ended (LEFT, ALUMNI or REMOVED) runs until it ended or until the last check-in, whichever is later, so a former club's rate doesn't decay over time. heldSinceJoined and rate use this window, and rate is capped at 1.
- Retention periods are in campus time. Academic years come from Term.academicYear and run back to back, so summer and the August gap belong to the year they follow. The current period is included and marked inProgress. Individual retention counts the period in progress only once the person has attended in it.
- Network: lines are undirected, and one check-in adds at most 1 to a line, so a member of both co-hosting clubs doesn't count twice. Membership is judged at the time of the event. Only APPROVED clubs are nodes. Size = check-ins at events the club hosted or co-hosted. Default window is the last 365 days.
- platformSummary: activeStudents = ACTIVE-status students who are active in at least one club by attendance (membership not required). Check-ins and events this term include university events. Cross-club check-ins = check-ins that drew at least one line.
- Club-level numbers include events the club co-hosted (attendance by occurrence, active students, retention, review eligibility, held counts), per 'co-hosted events count for the host and every approved co-host'. Attendance.clubId is not used, so co-hosts are always included.
- Performance: the network SQL builds its rows from the base tables, because joining CTEs led the planner to sort about 800k rows and take 10 s. It returns one row per pair of clubs, and a pure function turns those into line weights; a test proves that matches the per-check-in rule. The monthly check-ins query groups by (month, person) first to avoid a slow count(DISTINCT).
- React cache() is keyed on primitive arguments (sorted id strings and millisecond timestamps), and one 'now' is shared per request, so repeated calls on a page reuse the same queries.

**Decisions:**

- Default sort is A–Z: neutral to every club and predictable. Number sorts default to high-to-low, word sorts to A–Z. Missing values always sort last.
- Pilot / Inactive badges on cards appear only once the metrics layer returns a row for that club, so the page never guesses a status.
- The headline rating comes from clubListMetrics, so the list and the club page agree. The star breakdown is counted from visible reviews, falling back to their average until metrics has data. Metrics already excludes hidden reviews, so the two match.
- Review-bombing check counts low ratings created or edited inside the window (`updatedAt`), excluding hidden reviews, so editing an old review down also counts. It runs only when the new rating is at or below the low-rating cutoff.
- Editing a hidden review keeps it hidden. Faculty and alumni can't write reviews. Reporting a review needs only sign-in, one report per person; a review you wrote, or one already hidden, can't be reported.
- Signed-out visitors see reviews as 'A Weber State student', following the rule that profiles are for signed-in university accounts only.
- 'You're in!' shows once per page visit, only for clubs you join straight away (gated clubs get a 'request sent' toast instead), and only when `shouldPromptForApp` (lib/clubs/queries) allows it: a store link is set (`app.iosUrl` or `app.androidUrl`), the account is active, the user hasn't signed in on the app (`hasMobileApp`), and they haven't pressed 'Not now' in the last 30 days. The dashboard card, the check-in success card and Settings → Notifications use the same rule (Settings ignores the snooze). 'Not now' snoozes every prompt for 30 days; closing with X doesn't.
- Review form actions live next to the component (components/reviews/actions.ts) so ClubReviews works wherever it's embedded. Card and hero register/subscribe share app/clubs/actions.ts.
- Until a store link is set, /get-the-app says the app is on its way and what it will do; only sysadmins also see how to run the Expo Go test build. The QR code shows only once a store link is set, to everyone on desktop-width screens, not only signed-in users: it's equally useful either way and pointless on a phone. Signed-in users also see a confirmation if they've already used the app.
- Constitution and bylaws text is readable by anyone on the club page; attached PDFs are linked only if canViewFile allows. Featured files are filtered per viewer with canViewFile.
- Club event lists show what the viewer may see: public for everyone, university-wide when signed in, members-only for members and leaders. Approved co-hosted events are included.
- 'My clubs' means clubs where you're an active member, have a pending request, or hold a role.
- Retention shows the still-running month or quarter as a lighter 'so far' bar, so a half-finished period doesn't look like a drop. The landing check-ins chart does the same for the current month.

**Decisions:**

- Seat editing rules: anyone with `orgchart` can edit any seat's text. New seats are only OFFICER or AMBASSADOR. A seat's role never changes. President and VP seats can be renamed but never archived. A seat can't be archived while someone holds it or an unfinished election targets it. The holder limit can't drop below the current number of holders.
- 'Restore defaults' brings back missing or archived default seats and resets the default seats' names, responsibilities and default permissions. Core seats are matched by role, others by name. Custom seats and everyone's roles are untouched. 'Start from the default setup' only works when a club has no seats at all.
- Hand-off is available exactly when access.assignableRoles includes PRESIDENT: the sitting President, or an advisor/admin acting for the club. A suspended President must finish their training first. Co-presidents can only hand off their own seat. 'Become alumni' also ends any other roles the person holds in the club and sets their membership to ALUMNI.
- Placing an ambassador in a club whose College Ambassador seat is full raises that seat's holder limit by one (logged), so the college isn't blocked by the club's limit. The Club Representative seat is matched loosely by name, in case an org renames it.
- Election voters: for a member vote, active members per metrics.activeMemberIdsFor; if that set is empty (no attendance yet), every ACTIVE student member. For a leadership vote, current student President/VP/officers/ambassadors, who can't vote for themselves. Candidates must be ACTIVE student members, and current leaders for a leadership vote.
- Elections: the schema has no nomination-start field, so nominations open when the election is created and close when voting opens. Voting must open in the future and stay open at least an hour. Only one unfinished election per seat. Candidates can withdraw or edit statements only while nominations are open. Ballots can't be changed. Counts are hidden until voting closes.
- Applying a result replaces every current holder of the seat. A re-elected incumbent keeps their existing assignment and history, and the other holders' terms end (TERM_ENDED). The election is marked applied first so two people can't apply it at once, and it rolls back to closed if the role assignment fails. Tie-breaks record the tied candidate ids in the activity log.
- Turnout is frozen in the 'election.closed' activity log entry (votes and eligible voters), so later roster changes don't rewrite past results.
- Role history: academic years run July 1 to June 30 in campus time. Vacancies shorter than 7 days are treated as hand-off noise and not flagged. A current seat's vacancy shows as 'Vacant since …'. Holders are listed oldest first. Contributions belong to the role holder even when a leader adds them. Uploads from the dialog go to the uploader's own files with MEMBERS visibility (any signed-in WSU account can open them).
- Roster removal mirrors memberships.removeMember: people can't remove anyone at their rank or above, only admins can remove advisors, and nobody can remove themselves from this page (leaving the club is a separate action). The CSV includes every membership except declined requests, with a Status column.

**Decisions:**

- Videos use the platform's own embed node, not TipTap's YouTube extension, so every embed has one stored form. Raw YouTube/Google iframes in older or pasted HTML are converted into embeds when edited, and the sanitizer still keeps them (https only, short host list, sandboxed).
- Embeds live only at the top level of a document, which is where RichContent can swap them for live blocks. Inserting from inside a list or table places the embed after that block. An embed found nested in stored HTML from another source becomes a plain link.
- Images uploaded in the editor are saved with PUBLIC visibility (unguessable /api/files/ID URL), so they show wherever the text is shown, including public club pages. Documents uploaded in the editor default to PUBLIC, with a toggle for club members (club files) or signed-in Weber State accounts (personal files). Files picked from existing files keep their own visibility; readers without access see a 'no access' card.
- Upload scope defaults to the club's files when clubId is set, otherwise the writer's own files (overridable with fileScope). If a club upload is refused (no 'files' capability), it retries in the writer's own files and shows a toast.
- Event search with a clubId returns the club's own events, approved co-hosted events and university events. Without one, it returns every event the viewer can see. Drafts are never offered.
- Not-allowed cards never reveal the hidden item: no file name for a file you can't open, and no event title for an event you can't see.
- The sanitizer now allows only the 'tableWrapper' class (a stray Tailwind class like 'fixed inset-0' could otherwise overlay the page), blocks protocol-relative URLs, and checks embed attributes: known kinds only, and data-src must be http(s) or a site path (a map's src may be an address). Outside links get target=_blank rel=noopener noreferrer nofollow; Wildcat Clubs links (/clubs/…) stay in the same tab.
- Extra styling the editor and RichContent need (checklist layout, scrolling tables, placeholder, table-resize handles) ships as one React-hoisted <style href precedence> (RichStyles) instead of a globals.css edit. React dedupes it, so there's no flash of unstyled content and nothing needs adding to globals.
- The editor's hidden input is rendered once and then updated directly, because React re-applies defaultValue on every render and that would overwrite what the person typed. On form reset the editor reloads defaultValue right after the browser's own reset, which also restores checklist boxes.
- Office pastes (text plus a picture of the text on the clipboard) paste as text. Clipboard images upload only when there is no text.

**Decisions:**

- Pasted links are stored at the end of Event.descriptionHtml as one <ul data-type="eventLinks"> block, which survives the sanitizer. They are split back out for the editor, event page, ICS and Google. This avoids a schema change.
- University events (clubId null) have no co-hosts and no costs (BudgetItem.clubId is required). 'Members only' is saved as 'Weber State only' (UNIVERSITY), and the editor offers only Public or Weber State only.
- Rebuilding occurrences: if there are no occurrences yet, every meeting the rule produces is created, including past ones. A one-time event that moves is updated in place, keeping its id and check-in code. Repeating events never touch past meetings or meetings with check-ins. Upcoming meetings are matched to the new rule by campus date, keeping their codes, room changes and one-off cancellations; the rest are added or removed. New meetings of a cancelled event are created cancelled.
- Occurrences are rebuilt only when the meetings the rule produces change (compared by start and end, not rule fields). Saves that keep the times only add meetings the rule now produces (e.g. new terms) and never remove one, so extra meetings outside the rule (training makeups) survive. A one-time event whose occurrence has check-ins can't change its start (its end can).
- Cancelling an event marks its upcoming SCHEDULED meetings without check-ins cancelled, with the optional reason in EventOccurrence.note, tells accepted co-host clubs, and records the upcoming meetings that were already cancelled as keptCancelledIds in the event.cancelled ActivityLog data. Restoring brings back the other upcoming cancelled meetings, leaves those one-off cancellations (and their notes) alone, and reopens approval tasks for PENDING co-host invitations. Restoring one meeting of a cancelled event brings the whole event back (and reopens those tasks). cancelOccurrence refuses a meeting that has check-ins.
- Delete is refused when anyone has checked in, when any RoleRequirement (on or off) points at the training (deleting it would leave a TRAINING requirement nobody can meet), or when a cost line is locked by a funding request. The message tells the user to cancel instead.
- Costs: an event cost line covered by a SUBMITTED/APPROVED/PARTIALLY_APPROVED funding request is locked: the Events Builder shows it read-only, the domain refuses to change or remove it (lib/domain/events costLineLocks), and an event with a locked line can't be deleted (cancel it instead).
- Co-host rules: 'Invite all clubs' never withdraws invitations. With an explicit list, removing a club withdraws its invitation and cancels the task. A declined club stays declined unless removed and re-added. An accepted club can later stop co-hosting through decideCohost(approve=false). Invitations to every club go in-app and by push only, no email; single invitations also email.
- Calendars always show campus (America/Denver) time. FullCalendar runs in its 'UTC' zone and is fed offset-less campus wall-clock times, and selections and drags are converted back with campusDate.
- Calendar extendedProps.expectedCostCents = the per-meeting cost lines, plus the one-time lines on the event's first scheduled meeting. eventTotalCents is the whole event. Both appear only for viewers with the host club's events or budget capability.
- The public university feed includes only PUBLIC events, including PUBLIC university events, because a feed can't sign anyone in. A user's private token feed includes UNIVERSITY and members-only events they may see.
- Google Calendar copy: one Google event per platform event. The first scheduled meeting is the start and the rest are RDATEs, so semester rules and one-off cancellations copy exactly. The adapter records googleCalendarId and googleEventId itself; the domain stores a new Meet link in virtualUrl. Failures never block the save and show as a warning toast.
- The Meet-link request isn't stored, since there is no schema field. If Google sync is off, the event saves without a link, the UI explains the link comes once sync is on, and saving again then creates it. No link is ever made up.
- Drag and resize work only on upcoming (not yet ended), one-time, not-cancelled events that the viewer's club hosts. Repeating events open the editor instead.
- Quick-create from month view starts as a 6–7 PM meeting on that day. Selecting in the week view's all-day row makes an all-day event. Saving the full editor returns to the builder at the event's date.
- recurrence.ts: a rule with only a repeat count used to stop after one year. It now follows the count, within five years and the existing 400-meeting cap.
- University-event pages and admin pages accept a typed room like '404' and show it as 'Room 404', but leave seeded values such as 'Room 210' or 'Main Gym' alone (roomLabel).

- The club contact email (the club's Google account) is edited in Settings only. The profile editor shows it read-only with a link, so there is one input tool per piece of data. The create wizard still collects it once at founding.
- Drive, Calendar and Chat sync run as a club's Google account only for APPROVED clubs, and only after WSUSA verifies the account (Admin → Club reviews → club → Club Google account; an ADMINS task with sourceType 'googleAccount', opened on submission or when an involved club sets an address). Every adapter asks lib/integrations/google clubGoogleAccount(club) first.
- A custom constitution or bylaws upload asks for both the succession method and the join policy, pre-filled with the club's current values; both are applied when WSUSA approves. With no schema column for them, they are stored on the 'constitution.custom_submitted' ActivityLog row and read back by statedSettings().
- Custom uploads are version 0 until approved, then numbered max+1. Withdrawn or rejected uploads never use up a version number.
- Adopting builder documents replaces the current ones immediately (no WSUSA approval) and withdraws any custom upload of the same kind that is still pending (marked SUPERSEDED, task CANCELLED), so there is one source of truth.
- Approving a club requires that any department request has been handled, that an ACTIVE constitution and bylaws exist (pending custom uploads must be decided first), and that the club has an active advisor.
- Club names are unique (case-insensitive) only against SUBMITTED, CHANGES_REQUESTED and APPROVED clubs, so abandoned drafts don't hold a name. The slug comes from the name, avoids reserved words such as 'new', and never changes when the club is renamed.
- The club type can be changed in the profile editor until WSUSA approves the club (admins can change it any time). Changing the department cancels a stale departmentRequest task, and files a new one if the club is already past founding.
- Retiring also sets pending join requests to DECLINED, cancels pending advisor invites and the club's open tasks (except invoices, review moderation and officer-requirement tasks), and adds a note to cancelled occurrences. Requirement tasks are closed by the requirement sync, run right away for everyone whose roles ended (including ambassadors the club placed elsewhere), so their officer tests are excused too. A founding club uses the same flow, labelled 'Close this club draft'.
- Reinstating a previously approved club returns it to APPROVED and restores the members and leaders who were active when it retired (accounts still ACTIVE) as new role assignments, so the gap shows in role history. A club that was never approved goes back to DRAFT rather than skipping review.
- Submitting to WSUSA requires the profile capability, which presidents, VPs and advisors all hold during founding.
- Constitution drafts autosave about 1.5 seconds after the last change. Previewing the PDF or adopting saves first, so the PDF always matches what you see.
- Admins see only the club they arrived from in the 'Adopt for club' list (via ?club=), not every club on the platform.
- Forms that can return validation errors submit through onSubmit (useFormSubmit) rather than <form action>, because React 19 resets uncontrolled fields after a form action, which would clear what people typed. This also keeps the rich-text editor's hidden input from reverting after a profile save.
- Workspace, admin-review and draft page titles show the club or draft name only to people allowed to see it. Metadata resolves before the layout's sign-in redirect, and it was leaking private draft-club names.
- Profile 'Additional documents' let the uploader choose Everyone or Members only. Removing one takes it off the profile (SUPERSEDED) but the file stays in Club files. A custom constitution or bylaws file is visible to LEADERS until it is approved, then becomes PUBLIC.
- The default documents leave out specific WSU policy numbers and phone numbers I couldn't verify. They point to 'WSU policy', the 'WSU Student Code' and 'WSU Police' instead. GPA is a fill-in defaulting to 2.0 'or any higher minimum WSUSA sets'. Activity thresholds point to the platform's standards rather than fixed numbers, so changing system config never requires re-adopting.

**Decisions:**

- Scan passes: a live QR token is swapped for a signed, timestamped pass that's valid for 10 minutes, so a scan survives logging in or a slow tap. Passes are only ever minted from a live token, never from another pass, so reloading can't keep one alive. A photo forwarded to a friend still goes stale.
- No side effects on GET: /c/<code> only previews. After login, ?go=1 makes the page press the 'Check in' button once in the browser (a POST server action), then strips go=1 from the URL.
- Self check-in (code only) needs the event to allow it AND an active membership or current role in the host or an approved co-host club. University events with no co-hosts are QR or manual only. An expired scan still works as a self check-in for members.
- Alumni accounts can't check themselves in (brief: 'signed-in active account'); leaders can add them by hand.
- Auto-enroll applies to students only. Faculty/staff check-ins are recorded with membership 'NONE', since membership is a student role. If joining fails, the check-in still counts.
- Manual adds: allowed from when check-in opens, including after it closes. Timestamp is 'now' during the window, otherwise the event's start time. They close training requirement tasks and notify the person in-app only (no email or push). They don't auto-join, because joinClub must run as the person joining.
- Codes: any 4–12 letters and digits are looked up exactly, because real seeded codes like BUILD8 contain look-alike characters. Typo hints (length, 0/O/1/I) appear only after a failed lookup. Typed URLs like /c/abc-234 redirect to /c/ABC234.
- Live screen privacy: names show as 'Maya C.' because the whole room can read a projector. The screen also has an in-screen 'Add someone' panel; it's in-tree rather than a portal dialog so it works in fullscreen and above the screen's z-index.
- Co-hosted events appear in the co-host club's tracker, read-only. Only the host's leaders run check-in or edit the list. 'Tag all clubs' events count only clubs with an approved co-host row, same as metrics.
- Tracker numbers: the table mirrors lib/metrics exactly. Columns take memberAttendees, guests, membersAtTime and rate from clubAttendanceByOccurrence. Row rate = check-ins ÷ held events since the person got involved, the same rule as memberClubSummary, limited to the selected range. Past meetings of later-cancelled events show only if someone checked in.
- Layout: the tiles are explicitly 'this term'. The range filter sits below them and scopes the attendance-by-event chart, the table and the CSV export. The retention chart has its own Month/Quarter/Academic year/Year toggle, as the brief asked.
- Charts use a dataviz-validated pair on white: members #6b3fa0, guests #eb6834. Bars have a 4px rounded top and a 2px gap between stacked segments. The retention line is straight segments, since a curve overshot 100%. Each chart has a hidden table for screen readers, and the tracker table is the visible table version.
- /me/attendance: cross-club activity uses the network map's rule (events with any participating club you weren't a member of). **Decisions:**

- College Ambassadors orgs default to COLLEGE funding. The ARCHITECTURE §6 rule never covered that club type, and the org is set up at the college level. Every other type follows §6 unchanged.
- A request is for one semester and one funding source. Costs planned for another source can still be picked, which asks this source to cover them; the cost line itself doesn't change. The semester can't be changed after the request starts; to ask for another semester, start a new request.
- Submitted and approved requests lock their cost lines: the line can't be edited or put in a second request. Denied and withdrawn requests unlock them. Draft request rows link to the live cost line, and submitting re-reads the live budget and snapshots it, so later edits never rewrite what was submitted.
- Per-meeting event costs count in each semester's budget by the meetings scheduled in that semester (eventCostSummaries buckets). One-time event costs and general costs count once, in the semester they're filed under. Costs of event ideas and cancelled events follow eventCostSummaries; their cards show 'Idea' or 'Cancelled'.
- Requested totals include submitted, approved, partly approved and denied requests. Approved totals include approved and partly approved. Pending means submitted. Drafts and withdrawn requests count in none of these.
- Partial approval must be more than $0 and less than the amount requested. A note is required to partly approve or deny, and optional for full approval. Drafts never appear to admins (the admin page returns 404 for them).
- One invoice per request, for the approved amount. Numbers restart each campus (America/Denver) calendar year; a row lock plus a retry on the unique number keeps two admins from creating duplicates. Creating an invoice tells the club in-app only; marking it processed tells them by every channel.
- Invoice access: admins, or the club's budget holders. Retired clubs have no capabilities, so only admins can open a retired club's invoices.
- A request needs a justification of at least 20 characters before it can be submitted. Limits: $1,000,000 per cost line and $10,000,000 per request.
- Invoice PDF text never hyphenates, so names and amounts stay whole. The footer is built from separately placed fixed Texts because react-pdf 4.9 renders a fixed View holding a render-prop Text blank here.

**Decisions:**

- Who counts as a leader: a current Ambassador, Officer, VP, President or Advisor role in a club that isn't retired or rejected, so founders of clubs still being set up count. Admins (WSUSA) can direct-message any club leader in either direction and can start or join leader groups, since they rank above advisors. They get no access to club chats or other people's DMs.
- The direct-message rule works both ways and is checked again on every send. A DM where the rule no longer holds (you no longer share a club, the person graduated, or someone is no longer a leader) stays readable but becomes read-only, with a specific reason shown.
- An empty DM someone opened with you stays hidden from you until they actually write.
- Club chats don't send a notification for each message; they show up as unread counts only. DMs and leader groups send an in-app notification plus a push (no email), once per unread run.
- Alumni accounts and people listed as alumni in a club can read that club's chat but not post. Retired clubs' chats are read-only.
- Deleting a message erases its text and leaves 'Message deleted' in its place. You can edit your messages only while you can still post in the conversation.
- Leader groups hold up to 100 people with names up to 80 characters. Any current leader in the group can rename it or add leaders, and anyone can leave. There's no removing other people, to keep it simple.
- Phones and tablets: Return adds a new line and the Send button sends, because phone keyboards have no Shift+Enter. Computers use Enter to send and Shift+Enter for a new line.
- Polling: the thread checks every 3 s and backs off to 30 s while requests are failing; it pauses while the tab is hidden and catches up when it's shown. The list refreshes every 15 s and whenever the window regains focus. The server's cursor overlaps by 4 s so no message is missed, and the client ignores repeats it has already seen.
- The 'New' line marks where unread started when you opened the chat. The thread opens at that line when there's more unread than fits on screen, otherwise at the newest message.
- Google Chat copy: only club chats are mirrored; DMs and leader groups stay in the app. Messages are posted as the club's account in the form '*Name*: text', because adding every student to the space isn't needed. Each copy is given an id derived from our message id, so edits and deletes can find it. The space is created the first time the chat is used, and failures are only logged; they never block a send.
- Announcement live preview: a Write/Preview toggle (both panels stay loaded) that renders in the browser using the same frame readers see, with videos, documents, files and maps shown in place. Embedded events show a placeholder card, because their details are looked up separately for each reader once posted.
- Default audience is Members for both club and university announcements, the less-exposed choice.
- Editing an announcement doesn't notify anyone again; if the audience widens, only the newly reached people are notified. Pinning neither notifies nor marks the post as edited.
- University announcements for Everyone and for Signed-in accounts notify every active account. Alumni accounts aren't notified, but they still see signed-in-only posts in their feed.
- The dashboard feed puts pinned university announcements first, then everything else newest first, so pinning has an effect there.
- On the club page, 'See all' expands in place (up to 12 more announcements) rather than opening a separate archive page, since no such route is in my paths. Long announcements collapse behind 'Read more' over 600 characters on the club page and over 320 on the dashboard.
- Signed-out readers see an announcement author's name without a profile link, because profiles are for signed-in Weber State accounts only. Badges appear only on restricted posts: members-only or leaders-only club posts, and leaders-only university posts. Manager lists label every audience.

**Decisions:**

- The conversation store lives in lib/ai/conversations.ts (an owned path) and acts as the domain module for AiConversation/AiMessage. It checks ownership (someone else's conversation looks exactly like a missing one), validates ids and does the writes. Chat text is not written to the activity log because it's private; every action the assistant takes is logged by the domain function it calls.
- No schema change: AiMessage.role is a string, so the internal rows (tools = chip labels, actions = cards waiting for Confirm, notice = errors and refusals) sit alongside the user/assistant/system rows. Only the latter three are sent to Claude, stored verbatim and append-only.
- Read tools run immediately and loop. Write tools only prepare a card; the loop stops. When the person confirms, the tool is prepared again (so permission and state are checked as of that moment) and runs only if the card is unchanged. post_announcement compares a fingerprint instead, because its 'about N people notified' count can drift harmlessly. If anything changed, nothing runs and Claude is told to show a fresh card.
- If the person sends a new message instead of confirming, the waiting actions are declined, never run, and Claude is told so in the same user turn (tool results first, then the person's text). An action stuck in 'running' after a crash is reported as 'interrupted — check whether it went through'.
- The model is picked per turn with routeAssistant, and the whole turn stays on that model (including the continuation after Confirm and a retry) to keep the cache and thinking blocks. Effort is medium on both models so lookups happen reliably; max_tokens is 64,000; tool_choice is auto; thinking is adaptive with the thinking-binding-controls-2026-08-01 beta set to drop_block, so a deploy that changes the guide or a tool doesn't break existing conversations. No server-side fallbacks, per anthropic.ts.
- The context note is appended only when it differs from the last note the model actually read (day-level, so roughly once a day or after a membership or role change). A note whose request never got an answer is left out of later requests, so system messages always follow a user turn.
- Refusals: partial output is thrown away, a placeholder answer is stored so the history stays valid, and a friendly notice is shown (no retry). If an answer is cut off at the length limit, any tool calls in it don't run. API errors show a notice with 'Try again' when retrying could help; a successful retry replaces the error notice in the view. Answers with no visible text get a placeholder plus a notice.
- Concurrency: one turn at a time per conversation (an in-process lock on globalThis so separately bundled routes share it), plus a database row lock (SELECT … FOR UPDATE) when claiming an action, so a double click or a second tab can't run it twice. The client also blocks double submits and locks the history list while an answer streams.
- Cost guard: 150 model calls per user per hour, counted from AiUsage rows (one per model call). They're kept apart from the chat, so deleting a conversation doesn't reset the limit; they cascade only when the user is deleted. The server always finishes a turn even if the browser disconnects, so there's no 'Stop generating' button; a dropped connection reloads what was saved.
- Extra read tools beyond the brief (founding_status, club_health, org_chart, find_club_member, directory_lookup) cover the founder, admin ('Which clubs are at risk this term?') and assign-role flows. Member lookups are limited to the club's leaders.
- UI: on desktop the panel sits bottom-right and leaves the page usable; on phones it's a full-screen sheet that closes when a link is followed and doesn't pop up the keyboard. The open conversation is remembered per browser tab (sessionStorage, wrapped in try/catch). A dot on the launcher means a reply finished while the panel was closed. Approved actions trigger router.refresh() so the page behind the chat is up to date. Model tags show 'Haiku' or 'Sonnet' under each answer. Conversations can be deleted from the panel or the page (permanent, with a confirmation dialog).

**Decisions:**

- Policy versions count distinct published content. Publishing a policy whose title, summary, text or document differs from what was last published bumps the version. Re-publishing unchanged content keeps the number. The last-published fingerprint lives on the ActivityLog row (publishedHash), so no schema change was needed. Seeded policies with no log rows are treated as published as they are now.
- A policy's slug is editable only until it is first published, so links to it (including the footer's) never break. Published policies can't be deleted, only archived.
- Policy content is either written or uploaded, never both. Uploads must be PDF or Word, stored as public university files. PDFs preview inline; Word documents show as an open/download card.
- There are no separate draft revisions of a published policy, since the schema has no revision table. Editing a published policy and saving re-publishes it (with a version bump if the content changed). Saving as Draft unpublishes it. The button labels say which will happen.
- The library lists each policy once, under its first placement in a fixed order (General last), with its other placements as tags, so nothing is duplicated. Search covers title, summary, text and document name.
- Test results don't reveal which choices were correct; takers see correct/incorrect per question. This keeps retakes meaningful.
- Using up every attempt without passing marks the assignment COMPLETED, meaning the person finished taking it, and closes its task. Follow-up is left to the FAILED automations. The deadline job doesn't mark someone missed while an attempt they handed in on time waits for review, or while a timed attempt is still running.
- Two starts at once (double click or two tabs) keep the first attempt and delete the empty duplicate.
- Autosave sends each question's saves in order through a per-question queue and retries after failures. A manual Submit refuses to hand in while answers remain unsaved, with a clear message. Auto-submit at zero proceeds anyway, because the server only keeps what arrived before the deadline plus 15 seconds of grace.
- The submit confirmation appears only when questions are unanswered, as the brief asks. With every question answered, Submit test hands in directly.
- Compliance is one row per person per club, using their highest role there, the same rule getClubAccess uses for pausing. 'Permissions paused' therefore matches what the workspace enforces.
- Requirement changes and on/off toggles re-sync all holders in after(), so saves stay fast. Newly owed tasks notify the leader ('Officer requirement to finish'); moved due dates don't. Requirements are turned off rather than deleted, so their history stays.
- Option-distribution bars use emphasis rather than categorical color: correct options in brand-600, the rest in a quiet gray (#a8a1b0). Every bar carries its count and percentage as text and a 'Correct' check icon, so color is never the only cue. The dataviz validator's lightness and chroma checks are for categorical palettes and don't apply to an accent-plus-gray emphasis pair. The pair separates clearly (ΔE 39), and the gray's contrast warning is covered by the visible labels.
- Builder save/publish bars and the attempt clock bar are sticky: the clock at the top under the site header (with editor toolbars offset to sit below it), the action bars at the bottom, so neither covers the editors' sticky toolbars.
- Jobs run sequentially in a fixed order, deduplicated per process with an in-flight promise. Concurrent runs across servers stay safe because each write is guarded by a status condition.

- Members get their read-only view at /files/clubs/[slug], because the manage layout only admits leaders. Leaders who land there are redirected to the workspace. 'Copy link' on a club folder points at this route, so the same link works for members and leaders.
- 'Type-to-search' works like a desktop file manager: typing a name jumps to the matching item, and '/' puts the cursor in the search box. Search covers the whole space and is kept in the URL; in Trash and Shared with me the box filters the list in the browser instead.
- Delete and Cmd/Ctrl+Backspace move items to the trash, and Backspace goes up a folder. Moving to trash shows an Undo toast. The trash never empties on its own; only someone who manages the files can delete for good or empty it.
- Files that the club's records still use can't be trashed or deleted: active or pending constitution/bylaws/profile documents, and policy documents. Superseded versions can be cleaned up; deleting one sets ClubDocument.fileId to null.
- The default folders are created once per club, tracked with an activity row as the marker. Existing similar names count as already there (the seeded 'Flyers & Photos' counts as Flyers). Folders made this way are recorded as added by the club's creator. Retired and rejected clubs are left alone.
- Google Drive: copying runs after the response is sent, one club at a time and in order. Only files that end up Public get 'anyone with the link'; folders never do, because Drive passes a folder's access down to everything inside. Members and leaders-only items aren't shared member by member; members open them through the platform. Leaders get editor access on the club's Drive folder. Only the drive.file scope is needed.
- On touch screens a tap opens an item, checkboxes select, and a long-press opens the action menu. With a mouse, click selects and double-click opens.
- People who can't edit don't see editing actions in the menu at all; a mixed selection shows them greyed out. The number of items inside a folder is shown only to people who manage the files, so others don't count things they can't see.
- List columns and the icon grid size themselves by the pane's own width (container queries), not the window's, because the workspace nav and the explorer sidebar narrow the pane.

**Decisions:**

- JavaScript tabs (expo-router/js-tabs) instead of NativeTabs: the brief needs six tabs, Android's native bar allows five, and JS tabs look the same in the web preview.
- The mobile API is bearer-only (a request without `Authorization: Bearer` counts as signed out even if a web cookie exists), so CORS '*' is safe and the Expo web preview can call it.
- Added three endpoints beyond the brief: POST checkin/preview (so a scan survives signing in via the 10-minute pass, and the app can show the event before signing in), GET events/[id] (event detail; also accepts event ids because notifications link /events/<eventId>), and DELETE push-token (the per-phone notifications switch).
- A scan or a typed code checks in right away once signed in (scanning is the intent). A deep link opened from outside the app shows the event and waits for 'Check in', so a link alone never checks anyone in.
- The notifications switch is per phone: off deletes this phone's PushToken and remembers 'off' locally. The User model has no push preference, and email settings stay on the web.
- The server sends event times already labelled in campus time (dayKey, dayLabel, timeLabel, whenLabel), so phones in other time zones match the web. The client formats only a few instants itself, using Intl with America/Denver.
- Club-page upcoming events, Home 'coming up' and Calendar all come from lib/events/feed, so visibility and co-hosting match the web calendar. Cancelled meetings are left out of Home and club lists but shown struck-through with the club's note in Calendar.
- 'Not now' on a live prompt is remembered until the app closes and covers both the Home banner and the club pop-up (the web remembers it per session). After dismissal the club page keeps a small 'Check-in is open' row.
- The club-page pop-up checks in inside the sheet and shows the full result there. Home banners open the full check-in screen.
- The check-in result shows review progress until reviews unlock, and the 'You can now review' news only on the check-in that unlocks it.
