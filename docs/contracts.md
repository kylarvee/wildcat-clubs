# Builder contracts

Exported functions, components and routes each slice provides for the others. Generated from the builders' reports; the code is the source of truth.

## Metrics (lib/metrics)

- import from "@/lib/metrics" (server only). Functions whose at is optional use one shared 'now' per request when it's omitted.
- isMemberActive(userId: string, clubId: string, at?: Date): Promise<boolean> — the attendance rule only (true for a regular guest as well); pair it with membership status when the question is about members.
- activeMemberIdsFor(clubId: string, at?: Date): Promise<string[]> — ids of ACTIVE members who are active per the rule.
- clubActivity(clubId: string, at?: Date): Promise<ClubActivity> — adds optional currentTermName / previousTermName. reasons lists each unmet requirement when the club is inactive, holds the pilot note while it's in its pilot period, and is empty when it's active on its own record.
- NEW clubActivityMany(clubIds?: string[], at?: Date): Promise<Map<string, ClubActivity>> — batch for admin tables; leave out ids for every approved club.
- clubRetention(clubId: string, period: 'month'|'quarter'|'academicYear'|'year', opts?: { count?: number; at?: Date }): Promise<RetentionPoint[]> — oldest first, ending with the period that contains at (inProgress: true). Default counts come from DEFAULT_RETENTION_COUNT = { month: 12, quarter: 8, academicYear: 4, year: 4 }; rate is null when the previous period had nobody.
- memberRetention(userId: string, clubId: string, period: RetentionPeriod): Promise<{ periods: number; attendedPeriods: number; rate: number | null }> — the period in progress counts only once they've attended in it.
- clubAttendanceByOccurrence(clubId: string, opts?: { from?: Date; to?: Date }): Promise<OccurrenceAttendance[]> — oldest first. Defaults to every occurrence that has started (pass a future to for upcoming ones). Includes events the club co-hosted. Adds an optional held: boolean.
- NEW clubMemberAttendanceCounts(clubId: string, opts?: { from?: Date; to?: Date }): Promise<Map<userId, MemberAttendanceCount>> — MemberAttendanceCount = { attended: number; lastAttendedAt: Date | null; active: boolean }. Covers every ACTIVE member (zeros if they haven't come) plus everyone who has attended. attended and lastAttendedAt respect the range; active is always as of now.
- memberClubSummary(userId: string, clubId: string): Promise<MemberClubSummary>
- NEW memberClubSummaries(userId: string): Promise<MemberClubSummaryEntry[]> — MemberClubSummaryEntry = { club: { id, name, slug, logoColor, logoUrl }; summary: MemberClubSummary; membershipStatus: MembershipStatus | null }. Lists ACTIVE memberships first, then clubs they only attended or have left; each group alphabetical.
- reviewEligibility(userId: string, clubId: string): Promise<{ eligible: boolean; attended: number; required: number }>
- clubListMetrics(clubIds?: string[]): Promise<Map<string, ClubListMetrics>> — one batched pass. With no ids it covers every APPROVED club; with ids it covers those clubs in any status. retentionRate compares the last complete campus month with the one before.
- networkData(opts?: { since?: Date; until?: Date }): Promise<NetworkData> — default window is the last 365 days (NETWORK_DEFAULT_DAYS), shared between visitors for 60 s. Nodes are APPROVED clubs sorted by name; majorName falls back to the club's focusOther. Edges are undirected, source < target, sorted by weight descending.
- platformSummary(at?: Date): Promise<PlatformSummary> — adds optional termName. activeClubs includes pilot clubs (activeClubs + inactiveClubs = approved clubs). eventsThisTerm = held events, university events included. monthlyCheckins = last 12 campus months, labelled like 'Oct 2026'.
- Re-exported pure helpers: isActiveStudent(standing: { lastAttendedAt: Date|null; latestRank: number|null }, at: Date, rule: { windowDays: number; recentEvents: number }): boolean; pilotPeriodEnd(createdAt: Date, terms: TermLike[]): Date | null; attendanceRate(memberAttendees: number, membersAtTime: number): number | null; retentionRate(retained: number, previous: number): number | null; checkinLines(participants: string[], memberOf: string[]): [string, string][]
- Client-safe types: import type { ClubActivity, RetentionPoint, OccurrenceAttendance, MemberClubSummary, MemberClubSummaryEntry, MemberAttendanceCount, ClubListMetrics, NetworkNode, NetworkEdge, NetworkData, PlatformSummary, RetentionPeriod } from "@/lib/metrics/types" (also re-exported from "@/lib/metrics"). The pure rules are in "@/lib/metrics/pure", which has no server imports.

**Decisions:**

- Active student is 'attended in the window OR attended one of the club's last N events'. I read 'whichever is later' as: someone stays active until whichever comes later, N days after their last check-in or the moment that event drops out of the club's last N events. That is the same as the OR the contract describes; the stricter AND reading would have marked nobody active in clubs that meet every other month. The window is inclusive, and 'last attended' means the event's start time, not when the check-in was recorded.
- Event times are occurrence start times throughout, so a leader's late manual add counts on the day of the event.
- A held event is a SCHEDULED occurrence that has started and has at least one check-in, from an event that isn't a draft. Past occurrences of an event cancelled later still count when people checked in. Activity score counts only occurrences of events still SCHEDULED (host or approved co-host), from 30 days back to 30 days ahead.
- The active-club event minimum must be met within one term on its own (current term or previous activity term); it is not summed across the two. Current term = the term containing now, or the latest term between terms. Previous = the activity-counting term before it (summer skipped when it doesn't count).
- The pilot period ends at the end of the first activity-counting term that starts after creation, measured from creation as the contract says, and applies only to APPROVED clubs. If the calendar has no such term yet, the club counts as in its pilot with pilotEndsAt = null.
- A term end stored at campus midnight is treated as covering that whole day, so events on the last day count.
- Members at the time of an event: joinedAt at or before the start, not ended by then, any status except PENDING or DECLINED. Someone auto-enrolled by their first check-in joined after the start, so they count as a guest at that first event. This keeps member check-ins as a subset of members at the time, so the rate never exceeds 100%.
- 'Since joining' starts at the earlier of joinedAt and the first check-in, so guests who later join keep their history. A membership that ended (LEFT, ALUMNI or REMOVED) runs until it ended or until the last check-in, whichever is later, so a former club's rate doesn't decay over time. heldSinceJoined and rate use this window, and rate is capped at 1.
- Retention periods are in campus time. Academic years come from Term.academicYear and run back to back, so summer and the August gap belong to the year they follow. The current period is included and marked inProgress. Individual retention counts the period in progress only once the person has attended in it.
- Network: lines are undirected, and one check-in adds at most 1 to a line, so a member of both co-hosting clubs doesn't count twice. Membership is judged at the time of the event. Only APPROVED clubs are nodes. Size = check-ins at events the club hosted or co-hosted. Default window is the last 365 days.
- platformSummary: activeStudents = ACTIVE-status students who are active in at least one club by attendance (membership not required). Check-ins and events this term include university events. Cross-club check-ins = check-ins that drew at least one line.
- Club-level numbers include events the club co-hosted (attendance by occurrence, active students, retention, review eligibility, held counts), per 'co-hosted events count for the host and every approved co-host'. Attendance.clubId is not used, so co-hosts are always included.
- Performance: the network SQL builds its rows from the base tables, because joining CTEs led the planner to sort about 800k rows and take 10 s. It returns one row per pair of clubs, and a pure function turns those into line weights; a test proves that matches the per-check-in rule. The monthly check-ins query groups by (month, person) first to avoid a slow count(DISTINCT).
- React cache() is keyed on primitive arguments (sorted id strings and millisecond timestamps), and one 'now' is shared per request, so repeated calls on a page reuse the same queries.

**Decisions:**

- Default sort is A–Z: neutral to every club and predictable. Number sorts default to high-to-low, word sorts to A–Z. Missing values always sort last.
- Pilot / Inactive badges on cards appear only once the metrics layer returns a row for that club, so the page never guesses a status.
- The headline rating comes from clubListMetrics, so the list and the club page agree. The star breakdown is counted from visible reviews, falling back to their average until metrics has data. Metrics already excludes hidden reviews, so the two match.
- Review-bombing check counts low ratings created or edited inside the window (`updatedAt`), excluding hidden reviews, so editing an old review down also counts. It runs only when the new rating is at or below the low-rating cutoff.
- Editing a hidden review keeps it hidden. Faculty and alumni can't write reviews. Reporting a review needs only sign-in, one report per person; a review you wrote, or one already hidden, can't be reported.
- Signed-out visitors see reviews as 'A Weber State student', following the rule that profiles are for signed-in university accounts only.
- 'You're in!' shows once per page visit, only for clubs you join straight away (gated clubs get a 'request sent' toast instead), and only if the user hasn't signed in on the app (`hasMobileApp`) or dismissed the prompt before. 'Not now' is permanent, per the brief; closing with X isn't.
- Review form actions live next to the component (components/reviews/actions.ts) so ClubReviews works wherever it's embedded. Card and hero register/subscribe share app/clubs/actions.ts.
- The /get-the-app QR code shows to everyone on desktop-width screens, not only signed-in users: it's equally useful either way and pointless on a phone. Signed-in users also see a confirmation if they've already used the app.
- Constitution and bylaws text is readable by anyone on the club page; attached PDFs are linked only if canViewFile allows. Featured files are filtered per viewer with canViewFile.
- Club event lists show what the viewer may see: public for everyone, university-wide when signed in, members-only for members and leaders. Approved co-hosted events are included.
- 'My clubs' means clubs where you're an active member, have a pending request, or hold a role.
- Retention shows the still-running month or quarter as a lighter 'so far' bar, so a half-finished period doesn't look like a drop. The landing check-ins chart does the same for the current month.

**Decisions:**

- Seat editing rules: anyone with `orgchart` can edit any seat's text. New seats are only OFFICER or AMBASSADOR. A seat's role never changes. President and VP seats can be renamed but never archived. A seat can't be archived while someone holds it or an unfinished election targets it. The holder limit can't drop below the current number of holders.
- 'Restore defaults' brings back missing or archived default seats and resets the default seats' names, responsibilities and default permissions. Core seats are matched by role, others by name. Custom seats and everyone's roles are untouched. 'Start from the default setup' only works when a club has no seats at all.
- Hand-off is available exactly when access.assignableRoles includes PRESIDENT: the sitting President, or an advisor/admin acting for the club. A suspended President must finish their training first. Co-presidents can only hand off their own seat. 'Become alumni' also ends any other roles the person holds in the club and sets their membership to ALUMNI.
- Placing an ambassador in a club whose College Ambassador seat is full raises that seat's holder limit by one (logged), so the college isn't blocked by the club's limit. The Club Representative seat is matched loosely by name, in case an org renames it.
- Election voters: for a member vote, active members per metrics.activeMemberIdsFor; if that set is empty (no attendance yet), every ACTIVE student member. For a leadership vote, current student President/VP/officers/ambassadors, who can't vote for themselves. Candidates must be ACTIVE student members, and current leaders for a leadership vote.
- Elections: the schema has no nomination-start field, so nominations open when the election is created and close when voting opens. Voting must open in the future and stay open at least an hour. Only one unfinished election per seat. Candidates can withdraw or edit statements only while nominations are open. Ballots can't be changed. Counts are hidden until voting closes.
- Applying a result replaces every current holder of the seat. A re-elected incumbent keeps their existing assignment and history, and the other holders' terms end (TERM_ENDED). The election is marked applied first so two people can't apply it at once, and it rolls back to closed if the role assignment fails. Tie-breaks record the tied candidate ids in the activity log.
- Turnout is frozen in the 'election.closed' activity log entry (votes and eligible voters), so later roster changes don't rewrite past results.
- Role history: academic years run July 1 to June 30 in campus time. Vacancies shorter than 7 days are treated as hand-off noise and not flagged. A current seat's vacancy shows as 'Vacant since …'. Holders are listed oldest first. Contributions belong to the role holder even when a leader adds them. Uploads from the dialog go to the uploader's own files with MEMBERS visibility (any signed-in WSU account can open them).
- Roster removal mirrors memberships.removeMember: people can't remove anyone at their rank or above, only admins can remove advisors, and nobody can remove themselves from this page (leaving the club is a separate action). The CSV includes every membership except declined requests, with a Status column.

**Decisions:**

- Videos use the platform's own embed node, not TipTap's YouTube extension, so every embed has one stored form. Raw YouTube/Google iframes in older or pasted HTML are converted into embeds when edited, and the sanitizer still keeps them (https only, short host list, sandboxed).
- Embeds live only at the top level of a document, which is where RichContent can swap them for live blocks. Inserting from inside a list or table places the embed after that block. An embed found nested in stored HTML from another source becomes a plain link.
- Images uploaded in the editor are saved with PUBLIC visibility (unguessable /api/files/ID URL), so they show wherever the text is shown, including public club pages. Documents uploaded in the editor default to PUBLIC, with a toggle for club members (club files) or signed-in Weber State accounts (personal files). Files picked from existing files keep their own visibility; readers without access see a 'no access' card.
- Upload scope defaults to the club's files when clubId is set, otherwise the writer's own files (overridable with fileScope). If a club upload is refused (no 'files' capability), it retries in the writer's own files and shows a toast.
- Event search with a clubId returns the club's own events, approved co-hosted events and university events. Without one, it returns every event the viewer can see. Drafts are never offered.
- Not-allowed cards never reveal the hidden item: no file name for a file you can't open, and no event title for an event you can't see.
- The sanitizer now allows only the 'tableWrapper' class (a stray Tailwind class like 'fixed inset-0' could otherwise overlay the page), blocks protocol-relative URLs, and checks embed attributes: known kinds only, and data-src must be http(s) or a site path (a map's src may be an address). Outside links get target=_blank rel=noopener noreferrer nofollow; Wildcat Clubs links (/clubs/…) stay in the same tab.
- Extra styling the editor and RichContent need (checklist layout, scrolling tables, placeholder, table-resize handles) ships as one React-hoisted <style href precedence> (RichStyles) instead of a globals.css edit. React dedupes it, so there's no flash of unstyled content and nothing needs adding to globals.
- The editor's hidden input is rendered once and then updated directly, because React re-applies defaultValue on every render and that would overwrite what the person typed. On form reset the editor reloads defaultValue right after the browser's own reset, which also restores checklist boxes.
- Office pastes (text plus a picture of the text on the clipboard) paste as text. Clipboard images upload only when there is no text.

**Decisions:**

- Pasted links are stored at the end of Event.descriptionHtml as one <ul data-type="eventLinks"> block, which survives the sanitizer. They are split back out for the editor, event page, ICS and Google. This avoids a schema change.
- University events (clubId null) have no co-hosts and no costs (BudgetItem.clubId is required). 'Members only' is saved as 'Weber State only' (UNIVERSITY), and the editor offers only Public or Weber State only.
- Rebuilding occurrences: if there are no occurrences yet, every meeting the rule produces is created, including past ones. A one-time event that moves is updated in place, keeping its id and check-in code. Repeating events never touch past meetings or meetings with check-ins. Upcoming meetings are matched to the new rule by campus date, keeping their codes, room changes and one-off cancellations; the rest are added or removed. New meetings of a cancelled event are created cancelled.
- Cancelling an event marks its upcoming SCHEDULED meetings cancelled, with the optional reason in EventOccurrence.note, and tells accepted co-host clubs. Restoring brings back every upcoming cancelled meeting. Restoring one meeting of a cancelled event brings the whole event back.
- Delete is refused when anyone has checked in, or when an active RoleRequirement points at the training. The message tells the user to cancel instead.
- Co-host rules: 'Invite all clubs' never withdraws invitations. With an explicit list, removing a club withdraws its invitation and cancels the task. A declined club stays declined unless removed and re-added. An accepted club can later stop co-hosting through decideCohost(approve=false). Invitations to every club go in-app and by push only, no email; single invitations also email.
- Calendars always show campus (America/Denver) time. FullCalendar runs in its 'UTC' zone and is fed offset-less campus wall-clock times, and selections and drags are converted back with campusDate.
- Calendar extendedProps.expectedCostCents = the per-meeting cost lines, plus the one-time lines on the event's first scheduled meeting. eventTotalCents is the whole event. Both appear only for viewers with the host club's events or budget capability.
- The public university feed includes only PUBLIC events, including PUBLIC university events, because a feed can't sign anyone in. A user's private token feed includes UNIVERSITY and members-only events they may see.
- Google Calendar copy: one Google event per platform event. The first scheduled meeting is the start and the rest are RDATEs, so semester rules and one-off cancellations copy exactly. The adapter records googleCalendarId and googleEventId itself; the domain stores a new Meet link in virtualUrl. Failures never block the save and show as a warning toast.
- The Meet-link request isn't stored, since there is no schema field. If Google sync is off, the event saves without a link, the UI explains the link comes once sync is on, and saving again then creates it. No link is ever made up.
- Drag and resize work only on one-time, not-cancelled events that the viewer's club hosts. Repeating events open the editor instead.
- Quick-create from month view starts as a 6–7 PM meeting on that day. Selecting in the week view's all-day row makes an all-day event. Saving the full editor returns to the builder at the event's date.
- recurrence.ts: a rule with only a repeat count used to stop after one year. It now follows the count, within five years and the existing 400-meeting cap.
- University-event pages and admin pages accept a typed room like '404' and show it as 'Room 404', but leave seeded values such as 'Room 210' or 'Main Gym' alone (roomLabel).

- Adopting builder documents replaces the current ones immediately (no WSUSA approval) and withdraws any custom upload of the same kind that is still pending (marked SUPERSEDED, task CANCELLED), so there is one source of truth.
- Approving a club requires that any department request has been handled, that an ACTIVE constitution and bylaws exist (pending custom uploads must be decided first), and that the club has an active advisor.
- Club names are unique (case-insensitive) only against SUBMITTED, CHANGES_REQUESTED and APPROVED clubs, so abandoned drafts don't hold a name. The slug comes from the name, avoids reserved words such as 'new', and never changes when the club is renamed.
- The club type can be changed in the profile editor until WSUSA approves the club (admins can change it any time). Changing the department cancels a stale departmentRequest task, and files a new one if the club is already past founding.
- Retiring also sets pending join requests to DECLINED, cancels pending advisor invites and all of the club's open tasks, and adds a note to cancelled occurrences. A founding club uses the same flow, labelled 'Close this club draft'.
- Reinstating a previously approved club returns it to APPROVED and restores the members and leaders who were active when it retired (accounts still ACTIVE) as new role assignments, so the gap shows in role history. A club that was never approved goes back to DRAFT rather than skipping review.
- Submitting to WSUSA requires the profile capability, which presidents, VPs and advisors all hold during founding.
- Constitution drafts autosave about 1.5 seconds after the last change. Previewing the PDF or adopting saves first, so the PDF always matches what you see.
- Admins see only the club they arrived from in the 'Adopt for club' list (via ?club=), not every club on the platform.
- Forms that can return validation errors submit through onSubmit (useFormSubmit) rather than <form action>, because React 19 resets uncontrolled fields after a form action, which would clear what people typed. This also keeps the rich-text editor's hidden input from reverting after a profile save.
- Workspace, admin-review and draft page titles show the club or draft name only to people allowed to see it. Metadata resolves before the layout's sign-in redirect, and it was leaking private draft-club names.
- Profile 'Additional documents' let the uploader choose Everyone or Members only. Removing one takes it off the profile (SUPERSEDED) but the file stays in Club files. A custom constitution or bylaws file is visible to LEADERS until it is approved, then becomes PUBLIC.
- The default documents leave out specific WSU policy numbers and phone numbers I couldn't verify. They point to 'WSU policy', the 'WSU Student Code' and 'WSU Police' instead. GPA is a fill-in defaulting to 2.0 'or any higher minimum WSUSA sets'. Activity thresholds point to the platform's standards rather than fixed numbers, so changing system config never requires re-adopting.

**Decisions:**

- Scan passes: a live QR token is swapped for a signed, timestamped pass that's valid for 10 minutes, so a scan survives logging in or a slow tap. - No side effects on GET: /c/<code> only previews. After login, ?go=1 makes the page press the 'Check in' button once in the browser (a POST server action), then strips go=1 from the URL.
- Self check-in (code only) needs the event to allow it AND an active membership or current role in the host or an approved co-host club. University events with no co-hosts are QR or manual only. An expired scan still works as a self check-in for members.
- Alumni accounts can't check themselves in (brief: 'signed-in active account'); leaders can add them by hand.
- Auto-enroll applies to students only. Faculty/staff check-ins are recorded with membership 'NONE', since membership is a student role. If joining fails, the check-in still counts.
- Manual adds: allowed from when check-in opens, including after it closes. Timestamp is 'now' during the window, otherwise the event's start time. They close training requirement tasks and notify the person in-app only (no email or push). They don't auto-join, because joinClub must run as the person joining.
- Codes: any 4–12 letters and digits are looked up exactly, because real seeded codes like BUILD8 contain look-alike characters. Typo hints (length, 0/O/1/I) appear only after a failed lookup. Typed URLs like /c/abc-234 redirect to /c/ABC234.
- Live screen privacy: names show as 'Maya C.' because the whole room can read a projector. The screen also has an in-screen 'Add someone' panel; it's in-tree rather than a portal dialog so it works in fullscreen and above the screen's z-index.
- Co-hosted events appear in the co-host club's tracker, read-only. Only the host's leaders run check-in or edit the list. 'Tag all clubs' events count only clubs with an approved co-host row, same as metrics.
- Tracker numbers: the table mirrors lib/metrics exactly. Columns take memberAttendees, guests, membersAtTime and rate from clubAttendanceByOccurrence. Past meetings of later-cancelled events show only if someone checked in.
- Layout: the tiles are explicitly 'this term'. The range filter sits below them and scopes the attendance-by-event chart, the table and the CSV export. The retention chart has its own Month/Quarter/Academic year/Year toggle, as the brief asked.
- Charts use a dataviz-validated pair on white: members #6b3fa0, guests #eb6834. Bars have a 4px rounded top and a 2px gap between stacked segments. - Testing footprint: writes were tested only on a scratch database I created and dropped. On the shared database I only signed in as the seeded Priya persona in the browser pane (one session row) and only viewed pages.

**Decisions:**

- Meeting series: one weekly or biweekly series per club per fall and spring semester (Fall 2024 through Fall 2026), expanded with expandOccurrences, not one series running through summers. Labor Day, MLK Day, Presidents' Day, Thanksgiving and spring break dates are CANCELLED with a note; series end the Friday before finals.
- Term dates: Fall starts the last Monday of August; Spring starts the first Monday on or after Jan 5; both run 16 weeks including finals. Summer runs from 10 days after Spring ends to early August, with countsForActivity=false. Spring commencement is set one week after Spring ends (about May 1) and December graduation is the last day of Fall; these drive alumni status and GRADUATED role endings.
- Officer Policy Test has 10 questions: 8 choice (6 single, 2 multi), 1 short and 1 long answer, because the brief's 7+1+1 adds up to 9. Its intro embeds a public sample YouTube video labelled as a placeholder for WSUSA's own.
- Oscar's two REQUIREMENT tasks: the test is due about 10 days after seeding (30-day grace) and training about 25 days after (45-day grace). Both are open, he is inside grace, and he is kept out of training check-ins.
- Training makeup sessions: extra Club Officer Training dates every three weeks after each term's main session in the current academic year, plus one on a Wednesday about a week out. Without them, officers who start mid-semester would show as overdue. Only one chosen non-persona officer is past grace; the seed prints who.
- Guests: under ARCHITECTURE §6, a non-member who checks in at an open club becomes a member, so about 18% of open-club members joined through check-in (source CHECKIN, joinedAt equal to their first check-in). Cross-club network links come from shared memberships (sampled with strong same-college weighting) and from members of co-host clubs attending as guests.
- Personas are never picked at random for roles. Their histories are fixed (for example, Priya was Events Coordinator, then VP, then President; Gwen was VP, then President 2024–2026, ending GRADUATED). Generated students fill everything else, with continuations, December graduations, about 6% resignations, empty seats and refills. Former presidents are not later put in lower seats.
- Membership details: memberships that began before Fall 2024 use source IMPORT (as if rosters were imported when the platform started). Members of retired clubs become ALUMNI on the retirement date. Advisors get ADVISOR-source memberships and calendar subscriptions, as grantRole does. A college ambassador placement also settles any open join request in that club.
- The SWE closed election's winner is a different officer, not Vanessa, so applying it does not change her VP role. Sam has no notifications, so he really 'has nothing'. Officer permissions equal seat defaults.
- Check-in codes come from the seeded random generator (same alphabet as lib/attendance/token), with fixed codes for the three live or today events. checkinSecret uses generateCheckinSecret(), which is random, so QR tokens can't be predicted from the repository.
- Funding: event-linked budget items exist from Spring 2025 on. Funding requests cover every status (DRAFT, SUBMITTED, APPROVED, PARTIALLY_APPROVED, DENIED, WITHDRAWN) with snapshot items. Invoices are numbered WC-<year>-<4 digits> in order of creation; each invoice has an INVOICE task, DONE once processed.
- Policies: the 9 required slugs plus a DRAFT 'travel-and-off-campus-activities' and a PDF-only 'student-code-of-conduct-summary' (a university FileItem with no bodyHtml). Every body opens with the sample-policy notice.
- Determinism: the ids and the user and club rows came out identical on repeated same-day runs, and nothing else is seeded with system randomness. Whatever depends on the current date (past dates, recent activity, which officer's permissions are paused) changes with the day it runs; SEED_NOW reproduces a given day.
